# MirrorProxy 1.4.1

MirrorProxy 1.4.1 is a security and reliability maintenance release. It
hardens browser-authenticated control-plane mutations and OCI bearer-token
discovery, fixes the container Registry workbench, and makes scrollable console
surfaces use one consistent Tailwind design-system treatment.

## Highlights

### Browser control-plane CSRF protection

- Cookie-authenticated administrator and user mutations now require both a
  same-origin request and a session-bound HMAC CSRF proof.
- MirrorProxy issues separate `__Host-` CSRF cookies for administrator and user
  sessions, refreshes them with authenticated session responses, and clears
  them during logout or revocation.
- The embedded web console automatically attaches the correct proof to unsafe
  same-origin requests without exposing the HttpOnly session cookie.
- Bearer-token API clients remain supported and do not need browser CSRF
  headers when no session cookie is present.

### Safer OCI bearer-token discovery

- OCI authentication challenges are accepted only from the challenged
  registry origin or an explicit HTTPS token issuer trusted for that registry.
- Token endpoints with embedded credentials, fragments, untrusted origins, or
  non-HTTPS schemes are rejected.
- Token fetches do not follow redirects, use DNS addresses validated before the
  request, and reject loopback, private, link-local, carrier-grade NAT,
  documentation, benchmark, multicast, and other special-use IPv4/IPv6 ranges.
- New `oci_token_issuers` configuration provides safe defaults for Docker Hub,
  Elastic Registry, and GitLab Container Registry. Operators of a custom
  registry may add its external public token origin explicitly.

These controls close server-side request forgery paths in malicious or
compromised registry authentication challenges while retaining anonymous pulls
from the supported public registries.

### Container Registry workbench fixes

- Docker Hub shorthand and digest references such as `nginx:latest`,
  `owner/image:tag`, and `ubuntu@sha256:...` are recognized correctly instead
  of being mistaken for custom registry hosts.
- Selecting a registry now resets mode-appropriate Single Image, Compose YAML,
  and Dockerfile examples and keeps each editor mode's content independently.
- Compose and Dockerfile output labels now match the selected mode, while the
  selected registry has an explicit accessible pressed state.
- `FROM scratch` and unresolved variable references are preserved rather than
  rewritten into invalid proxy image paths.
- Docker Engine output clearly remains Docker Hub-only, and generated K3s YAML
  uses the supported MirrorProxy endpoint form.

### Consistent web-console scrollbars

- Replaced isolated hand-written scrollbar rules with the shared Tailwind
  `scrollbar-thin` design tokens.
- Applied the shared light and dark styling to the page, registry rail and
  output, installer and generated commands, configuration dialogs,
  administrator tabs, geographic target selectors and traffic charts, and
  source-health tables.
- Browser regression coverage now validates the generated 8px Tailwind
  scrollbar and Registry rail behavior.

### CI and release reliability

- Restored warning-free Clippy validation with Rust 1.98.
- Updated the real administrator API smoke to acquire and send the session CSRF
  proof before exercising protected mutations.
- The release candidate passed the frontend unit suite and production build,
  Playwright browser tests, Rust formatting, Clippy and workspace tests, real
  server/administrator smoke, dependency audits, coverage, public multi-client
  protocol smoke, and Linux, macOS, and Windows client tests.

## Compatibility and upgrade notes

- Existing routes, SQLite databases, cache data, account sessions, and standard
  public Registry configuration remain compatible; no database migration is
  required.
- Browser sessions receive the new CSRF cookie automatically when signing in
  or refreshing the current session. Custom browser integrations that mutate
  account or administrator APIs with a session cookie must echo the matching
  CSRF cookie in the `x-mirrorproxy-csrf` header and send a valid same-origin
  `Origin` or `Referer` header.
- Non-browser automation should continue using bearer authentication. It is not
  subject to the browser CSRF proof when no session cookie is supplied.
- Custom OCI registries whose bearer token service uses a different origin must
  add that HTTPS origin under the corresponding `oci_token_issuers` entry.
